# Adding an Import Format — Developer Guide

The import pipeline is format-agnostic downstream of the parser. Adding a
format is four steps, and **nothing after the parser changes** — no new
endpoint, no schema change, no store or hook edits. The brevity of this
procedure is the proof of that claim.

## 1. Implement `ParseFile`

Create `src/features/import-export/services/parsers/<format>Parser.ts`
exporting the shared signature:

```ts
import type { ParseFile } from "../../types/importExport.types"

export const parseMyFormat: ParseFile = async (file, options) => {
  // 1. Read the file. Any parsing library goes behind `await import()` —
  //    a user who never imports this format must never download it.
  // 2. Produce NormalizedFeature[] with geometry IN THE SOURCE CRS.
  //    Do not transform coordinates — ST_Transform runs server-side.
  // 3. If your raw features are GeoJSON-shaped, call normalizeFeatures()
  //    (see ./normalizeFeatures.ts) — it applies the six-type geometry
  //    vocabulary, attribute sanitization, and lenient per-feature issue
  //    reporting exactly as the other parsers do.
  return {
    features,          // NormalizedFeature[], source CRS
    detectedCrs,       // "EPSG:nnnn", "CUSTOM", or null → user must choose
    warnings,          // ImportIssueDraft[] — non-fatal findings
    // Optional: detectedCrsDefinition, columns (CSV-like), availableLayers
  }
}
```

Rules the other four parsers follow, and yours must too:

- **Lenient by default**: an unreadable feature becomes an issue with its
  source position; it never aborts the file (FR-006).
- **Honour `options.signal`** — check it every few thousand features so
  cancellation stays under the 2-second budget.
- **Archive formats**: run `assertArchiveEntryPath` on every entry name and
  `assertExpansionRatio` cumulatively *before* extraction (`utils/fileGuards`).
- **Positions users can find**: 0-based feature index, or 1-based line numbers
  for line-oriented formats (FR-033).

## 2. Register content-based detection

Extend `detectFormat` in `utils/fileGuards.ts` to recognize the format by
**content** (magic bytes or structural probe) — never by extension alone — and
add the format literal to `importSourceFormatSchema` in
`src/shared/contracts/importJob.schema.ts` (the one server-side touch: a wider
enum, no handler change).

## 3. Route it in the worker

Add a `case` to `loadParser` in `services/importParser.worker.ts` with a
**literal** import specifier (bundlers can only code-split literal dynamic
imports):

```ts
case "myformat": {
  const { parseMyFormat } = await import("./parsers/myFormatParser")
  return parseMyFormat
}
```

## 4. Fixture + tests

- A **real** fixture file in `__tests__/fixtures/` — generated by a real
  writer, not hand-mocked bytes.
- A parser unit suite (`parsers/__tests__/<format>Parser.test.ts`) covering the
  happy path, each rejection category, and cancellation.
- One integration test running the fixture through
  create → chunks → complete against the test database (copy the shape of
  `kmlImport.integration.test.ts`).

That's the whole procedure. If you find yourself editing `useImport`, the chunk
endpoint, the repository, or the dialogs, the new format is leaking past the
parser boundary — stop and put the difference inside the parser instead.
